# 系统架构说明

## 1. 当前定位

`sci-data-logger` 最初是一个面向湿实验记录的智能处理框架，核心目标是把：

- 手写实验本图片；
- 扫描 PDF；
- 仪器文件；
- 用户补录信息；

汇合成结构化、可审核、可追溯的实验记录。

在当前版本中，项目已经进一步演进为：

> **以稳定湿实验主干为核心、通过外挂扩展逐步覆盖不同用户和不同实验范式的科研记录平台。**

因此，当前架构不再只是单条“输入 → 解析 → 入库”流水线，而是分成：

1. **冻结主干（core）**
2. **外挂扩展层（extensions）**
3. **面向用户的入口层（workbench）**

---

## 2. 总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│ extensions/workbench/                                        │
│ 面向用户的网页入口：用户切换、上传、结果解释、规则编辑        │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ extensions/personalization/   extensions/drylab/              │
│ 个性化规则层                  干实验记录与研究关联层          │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ src/sci_data_logger/                                         │
│ 冻结主干：湿实验解析、编排、审核、SQLite / API                │
└──────────────────────────────────────────────────────────────┘
```

### 设计原则

- **主干冻结**：默认不修改 `src/sci_data_logger/` 下的既有核心模块；
- **外挂优先**：新增能力优先放入 `extensions/<domain>/`；
- **兼容优先**：扩展通过已有 ID、公开服务或 sidecar 数据与主干协作，不强行改动核心 schema；
- **体验分层**：领域能力与用户入口分开，避免“规则逻辑”和“页面逻辑”互相缠绕；
- **渐进演化**：先让新方向独立跑通，再判断是否值得形成最小公共接入点。

---

## 3. 主干（`src/sci_data_logger/`）

主干继续负责原项目最核心的湿实验能力：

### 数据流

1. 用户上传实验记录本图片、扫描 PDF 或仪器文件；
2. `DocumentProcessor` 将页面转换为 `PagePacket`；
3. `InstrumentService` 根据仪器注册表选择适配器，生成 `MeasurementPacket`；
4. `Normalizer` 将原始仪器字段映射为统一字段；
5. `ExperimentOrchestrator` 汇合页面、测量和用户补录信息，生成 `ExperimentRecord`；
6. `repository` 将记录保存到主 SQLite；
7. `review_issues` 与 `evidence_refs` 支持后续人工审核。

### 关键对象

- `PagePacket`：页面级解析结果；
- `MeasurementPacket`：仪器文件解析结果；
- `ExperimentRecord`：湿实验主对象；
- `ExperimentEvent`：实验时间线中的原子事件；
- `Material` / `Instrument`：跨页合并后的目录对象；
- `EvidenceRef`：字段来源与证据；
- `ReviewIssue`：需要人工确认的问题。

### 主干边界

主干当前只负责：

- 湿实验解析；
- 事件时间线重建；
- 主实验记录入库；
- 审核流程；
- 现有 API / CLI。

它**不直接承担**：

- 用户个性化配置；
- 干实验元数据管理；
- 额外 UI 工作台；
- 各扩展自己的 sidecar 数据。

---

## 4. 外挂扩展层（`extensions/`）

### 4.1 `extensions/personalization/`

目标：让系统适配不同研究者、实验类型和仪器习惯。

当前职责：

- 用户 profile；
- 实验模板；
- 仪器模板；
- 共享模板 + 本地覆盖；
- 配置优先级合并；
- 术语归一；
- 个性化必填字段检查；
- 个性化分析结果写入 sidecar DB。

当前规则合并顺序：

```text
默认规则 → 课题组模板 → 实验模板 → 仪器模板 → 用户覆盖
```

扩展数据默认位于：

```text
.local_data/extensions/personalization/
```

### 4.2 `extensions/drylab/`

目标：把 LAMMPS 等干实验记录纳入统一科研记录体系。

当前职责：

- `ResearchCase`
- `ResearchLink`
- `SimulationRun`
- `SimulationAsset`
- LAMMPS 目录导入；
- 湿实验与干实验关联；
- 查询、查看和 CSV 导出。

扩展数据默认位于：

```text
.local_data/extensions/drylab/
```

当前阶段它主要承担：

> **科研元数据管理层**

尚未完全进入：

> **科学结果深度理解层**

### 4.3 `extensions/workbench/`

目标：把已有个性化能力变成课题组成员可直接使用的轻量网页入口。

当前职责：

- 共享电脑上的用户切换；
- 湿实验记录上传；
- 模板选择；
- 个性化分析结果展示；
- 个人 profile 基础编辑；
- “系统如何理解我”的人话解释。

`workbench` 不重新实现湿实验解析，也不接管主数据模型；它只编排：

- 主干已有湿实验能力；
- `personalization` 的规则能力；
- 自己的轻量 UI。

## 5. 跨层协作方式

### 5.1 湿实验主流程

```text
用户上传记录
  ↓
主干解析并生成 ExperimentRecord
  ↓
personalization 根据当前用户 / 模板生成个性化分析
  ↓
workbench 用更友好的方式展示结果
```

### 5.2 湿干实验关联

```text
ExperimentRecord.experiment_id
  ↕
ResearchLink
  ↕
ResearchCase / SimulationRun
```

这种设计刻意没有让 `ExperimentRecord` 直接包含干实验字段，而是通过逻辑关联保持松耦合。

### 5.3 数据存储策略

| 数据类型 | 存储位置 |
|---|---|
| 主湿实验记录 | 主 SQLite |
| 个性化 profile 与分析记录 | personalization sidecar SQLite + 本地 JSON |
| 干实验案例与模拟记录 | drylab sidecar SQLite |
| 工作台当前用户选择 | 浏览器本地状态 |

这套策略的目的，是让新能力在探索阶段先独立成长，而不是一开始就把所有东西压进主 schema。

## 6. 扩展协作规范

每个扩展模块应尽量自带：

- 自己的入口；
- 自己的模板 / 配置；
- 自己的测试；
- 自己的本地持久化；
- 自己的说明文档。

如果多个扩展需要复用同一能力，应优先考虑：

1. 是否可以通过已有公开服务协作；
2. 是否需要抽取新的共享扩展层；
3. 是否真的有必要修改主干。

只有在扩展已经足够稳定、且团队确认确实需要统一接入时，才考虑向主命令或主 API 增加**最小、向后兼容**的入口。

---

## 7. 当前优势与权衡

### 优势

- 支持多人、多 agent 并行开发；
- 降低主干回归风险；
- 新方向可以快速试错；
- 便于针对不同研究者做个性化；
- 为湿实验与干实验统一留下了空间。

### 权衡

- 扩展之间会出现更多“边界管理”成本；
- 配置来源可能逐步增多，需要持续文档化；
- sidecar DB 让早期演化更轻，但后期可能需要统一查询层；
- 如果外挂数量继续增长，未来需要一份更薄的 extension contract。

---

## 8. 建议的后续演进

### 近期

1. 继续打磨 `workbench` 的上手体验；
2. 完善 `personalization` 的模板解释与推荐；
3. 继续增强 `drylab` 的解析能力。

### 中期

1. 设计轻量 extension contract；
2. 统一“共享模板 / 本地覆盖 / 主干配置”之间的边界说明；
3. 评估是否需要跨扩展查询层。

### 长期

1. 判断哪些能力已经足够稳定，值得形成最小公共接入点；
2. 在不牺牲主干稳定性的前提下，逐步把项目升级为更完整的科研记录平台。
