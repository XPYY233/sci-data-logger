# Extension Contract for Future AI Agents

> **必须先读**：如果你是来为本仓库新增、修改、评审任何 `extensions/` 相关工作的 AI agent，**在开始分析、规划或改代码之前，先完整阅读本文件**。  
> 本文件是当前仓库对外挂开发的最高优先级协作约定；若与零散旧笔记冲突，以本文件和 [`collaboration_guidelines.md`](collaboration_guidelines.md) 为准。

---

## 0. 先做什么

开始任何扩展工作前，按顺序完成：

1. 阅读本文件；
2. 阅读 [`collaboration_guidelines.md`](collaboration_guidelines.md)；
3. 阅读 [`../architecture.md`](../architecture.md)；
4. 再阅读与你当前任务直接相关的扩展文档与代码。

如果你还没有完成以上步骤，**不要开始设计实现方案，也不要直接改代码**。

---

## 1. 当前项目结构

本仓库采用：

> **主干冻结、外挂优先、兼容优先**

### 主干

```text
src/sci_data_logger/
```

主干负责：

- 湿实验解析；
- 事件时间线重建；
- 主实验记录入库；
- 审核 API / CLI；
- 已有核心 schema。

### 当前外挂

```text
extensions/personalization/
extensions/drylab/
extensions/workbench/
```

- `personalization`：用户 profile、模板、规则合并、个性化分析；
- `drylab`：干实验 / LAMMPS 记录与研究关联；
- `workbench`：面向用户的轻量网页工作台。

## 2. 不可违反的硬约束

### 2.1 默认不得修改主干

除非用户明确要求、并且任务本身已经说明需要团队级接入，否则：

- 不要修改 `src/sci_data_logger/`；
- 不要为了方便把扩展字段塞进主 schema；
- 不要把扩展 UI 或扩展 API 直接揉进主干；
- 不要让外挂反向依赖主干内部私有实现细节。

### 2.2 新能力优先做成外挂

新功能默认放在：

```text
extensions/<domain>/
```

并尽量自带：

- 入口（CLI / Web / API）；
- 模板或配置；
- sidecar 持久化；
- 测试；
- 文档。

### 2.3 扩展之间保持松耦合

优先通过以下方式协作：

- 已有公开服务函数；
- 稳定 ID；
- JSON 结果；
- sidecar 边界；
- 清晰的数据引用。

避免：

- 直接读取别的扩展的私有内部状态；
- 为了一个局部需求强行改别人模块的核心数据结构；
- 在多个扩展里重复实现同一种通用能力。

## 3. 开工前必须回答的 6 个问题

在你动手之前，先在自己的推理中明确：

1. 这个需求应该属于现有哪个扩展，还是应该新建扩展？
2. 它是否真的需要碰主干？如果不是，如何完全外挂完成？
3. 它会新增哪些公开入口、配置、sidecar 数据或文档？
4. 它需要和哪些现有扩展交互？交互边界是什么？
5. 如果未来别人继续扩展，它留下的是清晰接口还是隐式耦合？
6. 它是否保持了现有主干在“不加载扩展时仍可独立运行”的能力？

如果这些问题还没想清楚，不要急着编码。

---

## 4. 新扩展的最低交付标准

一个新的外挂模块，至少应该包含：

```text
extensions/<domain>/
  __init__.py
  ...
```

并尽量具备：

1. **明确职责**
   - 一句话能说清它解决什么问题；
2. **独立入口**
   - 例如独立 CLI、独立 Web app、或可复用 service；
3. **独立数据**
   - 默认写入 `.local_data/extensions/<domain>/`；
4. **共享模板与本地覆盖边界**
   - 可提交公共模板；
   - 个人配置只写本地；
5. **测试**
   - 能验证主干未被破坏；
   - 能验证扩展自身可独立运行；
6. **文档**
   - 至少有一个使用说明或架构说明。

## 5. 修改现有扩展时的规则

### `personalization`

适合放：

- 用户 profile；
- 模板；
- 规则合并；
- 个性化解释；
- 个性化分析。

不要放：

- 通用主干 schema；
- 干实验专属逻辑；
- 大型 UI 页面。

### `drylab`

适合放：

- LAMMPS / 模拟目录导入；
- 干实验案例；
- 湿干实验关联；
- 干实验查询与结果提取。

不要放：

- 湿实验个性化规则；
- 通用用户入口；
- 直接修改 `ExperimentRecord`。

### `workbench`

适合放：

- 面向用户的入口；
- 页面编排；
- 调用现有能力后的结果解释。

不要放：

- 重新实现湿实验解析；
- 重写个性化规则引擎；
- 接管别的扩展的业务数据。

## 6. 什么时候才允许考虑改主干

只有同时满足以下条件时，才可以提出“最小接入主干”的方案：

1. 需求已经在外挂层被验证有稳定价值；
2. 多个扩展都确实需要同一个核心能力；
3. 通过外挂边界继续绕行会造成明显重复或错误风险；
4. 改动可以做到：
   - 向后兼容；
   - 面积极小；
   - 不破坏主干在无扩展情况下独立运行；
5. 用户或团队明确同意。

否则，默认继续外挂。

---

## 7. 工作时的优先级

当多个目标冲突时，按以下顺序取舍：

1. **不破坏主干稳定性**
2. **不妨碍他人并行工作**
3. **保持模块边界清楚**
4. **再追求局部实现优雅**
5. **最后才是单次开发速度**
