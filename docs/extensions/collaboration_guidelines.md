# 扩展协作规范

本仓库当前采用“**主干冻结、外挂优先、兼容优先**”的扩展策略。

## 1. 主干边界

- 默认不修改 `src/sci_data_logger/` 下的现有核心模块。
- 新功能优先放入 `extensions/`，以独立命令、独立配置和独立 sidecar 数据库交付。
- 如果未来确实需要并入主 CLI 或主 API，必须先经过团队确认，并只增加向后兼容的最小接入点。

## 2. 扩展模块要求

每个扩展模块应尽量自带：

- 自己的命令入口；
- 自己的模板 / 配置；
- 自己的测试；
- 自己的本地持久化；
- 一份说明文档。

扩展运行时数据默认写入 `.local_data/extensions/`，避免污染版本库。

## 3. 配置与兼容

- 公共模板可提交到仓库；个人覆盖配置只保存在 `.local_data/extensions/`。
- 共享模板必须可在无本地配置时独立工作。
- 扩展模块不得假设主干 schema 已被修改；与主项目交互时优先通过已有 ID 建立逻辑关联。

## 4. 多 agent 协作建议

- 一个 agent 优先只负责一个扩展域，避免同时改多个模块。
- 新增扩展时复用 `extensions/<domain>/` 模式，不复制主干实现。
- 如果两个扩展都需要同一能力，先讨论是否沉淀为新的公共扩展层，而不是各自私有实现。

## 5. 当前已落地的扩展

- `extensions/personalization/`：湿实验个性化配置与 CLI。
- `extensions/drylab/`：干实验 / LAMMPS 记录与 `ResearchCase` 关联层。
- `extensions/workbench/`：完全外挂的湿实验个性化网页工作台。
