总体观察

1. 模型对实验本的整体识别能力

  • 测试集是重度手写中文 + 化学式 + 表格 + 多日累积记录 + 笔迹涂改的真实实验本（钠电池正极、锂离子超离子导体两个方向）。
  • 4/5 全部识别到 page_type synthesis_note、原文复刻 ≥95% 正确（化学式 Li2.25Zr0.75In0.25Cl6 这种非常细节的下标都没错）、给出了 confidence、给出了 open_questions。这远比单纯 OCR 强 —— 模型在主动做语义抽取与"我不确定"的元认知报告。
  • 失败模式只有一个：首张大图 timeout 363s，是网关/网络偶发慢，不是识别能力问题。

2. extracted_facts 是否抓到实验本核心字段

字段类型 出现于 实际命名

核心字段都抓到了。但跨图都是各取各的名字、各取各的结构 —— 这是下面"一致性"问题的重点。

3. prompt 的 JSON schema 约束力（这是当前最大问题）

PAGE_ANALYSIS_PROMPT 只给了 5 句话指令 + 一个 5 行示例：

{
  "page_type": "synthesis_note",
  "text_blocks": ["..."],
  "table_blocks": [{"title": "...", "rows": []}],
  "extracted_facts": {
    "sample_id": {"value": "...", "unit": null, "confidence": 0.8},
    "temperature": {"value": 500, "unit": "C", "confidence": 0.7}
  },
  "open_questions": ["..."]
}

这个 schema 太弱，导致：

  1. extracted_facts 的 key 完全自由命名。4 张图里出现了 39 个不同 key，没有任何重复。下游 agent 想拼装 ExperimentRecord（schemas.py::ExperimentRecord，里面有固定的 materials / steps / measurements / observations）几乎只能再过一遍 LLM 做映射。
  2. extracted_facts.value 类型从 string / int / float / list / dict 都有，FieldValue 模型本身允许（value: Any），但下游不知道该用什么 parser。
  3. table_blocks.rows 一会儿是 list[list[str]]，一会儿是 list[dict]。
  4. 当同一字段在一页里有多个值时（如图 3 的多天预烧温度），模型被迫挑一个标量，损失信息。
  5. 没有 review_required、warnings 写出指引 —— 4 张图全是 review_required=False / warnings=[]，可是图 3 模型自己都说"笔迹像 500，但可能是 900"。这种存在歧义的页面理应触发 review_required=True —— 当前 prompt 没要求模型这么做。
  6. 没有要求 schema 跟项目里的 materials / steps / observations 三个核心列表对齐。模型并不知道下游有 MaterialInput、ProtocolStep、MeasurementPacket、FieldValue 这些 pydantic 模型存在。

4. 跨图一致性

  • page_type 一致：全是 synthesis_note（其实图 5 应该是 characterization_note + synthesis_note 混合，里面有 EIS 测试）。prompt 里给的几个枚举值 synthesis_note / characterization_note / calculation / observation / unknown 太粗，没有要求"一页可以有多个类型，请用 list"。
  • extracted_facts.key 完全不一致：4 张图 39 个 key，0 个重叠。
  • table_blocks.rows 结构不一致：图 2/3 用 list[list]，图 4 用 list[list]，图 5 用 list[dict]。
  • value 类型不一致：百分比一会儿是 [7,9,10]，一会儿是 "1%, 2%, 8%, 10%"。
  • 优点：confidence 给得相当稳定，0.8~0.95 居多，跟用户笔迹清晰度大致正相关。

5. 如果改 X 就能更好（按 ROI 排序）

优先级 改动 预期收益
P0 在 prompt 里固化 extracted_facts 的 key vocabulary（至少分三组：materials, steps, observations, conditions），并在 schema example 里列出真实业务命名（如 target_material、precursor、mass、temperature、time、atmosphere、furnace_id、heating_rate、milling_rpm …）。让下游不再需要做语义对齐。 跨图字段统一，下游可以直接 map → ExperimentRecord
P0 在 prompt 里要求 table_blocks.rows: list[list[str]]（固定），并指定第 0 行是表头。 下游表格 parser 不再需要类型嗅探
P0 在 client 加大图自动 downscale（如 长边 > 2000px 缩到 1600px）或者把 timeout 拉到 240s + 客制化 retry 信号。 减少 timeout，本次 1/5 失败率（20%）变成 0
P1 在 prompt 里把"模型自报歧义时必须 review_required=true"写死。当前模型会写 open_questions，但 review_required 始终 False，UI 层很难触发人工 review。 自动触发审核流程
P1 把 extracted_facts 拆成三段或重命名为 extracted_materials / extracted_steps / extracted_conditions，对应 MaterialInput / ProtocolStep / FieldValue。 DocumentProcessor → ExperimentRecord 可直接 map，少一层 LLM
P1 允许字段值是 list of timepoint records（解决图 3 多日不同预烧温度被压成标量的问题）：{"value": [{"date": "...", "value": ..., "unit": ...}]} 真实跨日实验本能完整还原
P2 允许 page_type 是 list（图 5 是合成 + EIS 混合页）。 多用途页面分类正确
P2 把 STEP_EXTRACTION_HINT 里那些动词词表（称量、混合、搅拌、加热…）合并进 PAGE_ANALYSIS_PROMPT，让 step 抽取更可控。 step 字段标准化
P2 把围栏 ```json ... ``` 在 prompt 里明确写"只输出 JSON 对象，不要 markdown 围栏" —— 当前 parse_first_json_object 是兜底解析，能扛但是不优雅。 节省 1~2% token、解析更稳。
P3 reasoning_tokens 占 completion 的 40~70%，可考虑降级到 qwen-vl-max-latest（无 reasoning 阶段）以省 token & 减时延，看准确度损失再决策。 速度 ↑ / 成本 ↓

6. 一句话总结

Qwen3.6-plus 对实验本图像的语义识别能力已经远超 OCR，能复刻化学式、识别涂改、给出 confidence 和 open_questions —— 但 prompt/schema 的弱约束让"提取出的字段命名/类型/结构跨图各不相同"，是当前阻碍下游 ExperimentRecord 自动拼装的最大瓶颈。最优先 ROI 改动是把 extracted_facts 的 key vocabulary 与 table_blocks.rows 结构在 prompt 里固化。
